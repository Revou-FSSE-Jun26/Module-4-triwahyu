# Database Guidelines

Scope: everything under `backend/app/models/` and `backend/migrations/`.
Every guideline has a **Rule**, a **Rationale**, and a concrete RevoTask **Example**.
Rule IDs (`DB-xx`) are referenced by `scripts/check_guidelines.py` and the violation report.
Ownership: this file owns the data layer only. HTTP, validation and secrets live in `backend.md`.

## DB-01 Use a UUID primary key on every table

**Rule:** Every table has `id = db.Column(db.Uuid, primary_key=True, default=uuid.uuid4)`.
**Rationale:** UUIDs cannot be enumerated or guessed from a URL and are safe to generate client-side or across environments. Sequential integers leak record counts.
**Example:** `Card.id` is a UUID, so `PATCH /api/cards/<id>/position` never exposes how many cards exist.

## DB-02 Declare timestamps explicitly on every entity

**Rule:** Every entity table defines `created_at` and `updated_at` as `db.DateTime(timezone=True)`, non-null, defaulting to `utcnow()`, with `onupdate=utcnow` on `updated_at`. Declare the columns in the model itself, not through a hidden mixin.
**Rationale:** Audit questions ("when did this card change?") need an answer without reading logs. Explicit columns make the model readable on its own and checkable by script.
**Example:** `Card` declares `created_at`, `updated_at`, and `deleted_at` directly in `models/card.py`.

## DB-03 Delete content softly

**Rule:** `Board`, `Column`, `Card` and `Comment` carry a nullable `deleted_at`. Services set it instead of issuing `DELETE`, and every read filters `deleted_at.is_(None)`. Deleting a parent soft-deletes its children in the same transaction with the same timestamp.
**Rationale:** User-owned content must be recoverable, and a hard cascade would silently destroy comments and history (see `docs/contracts/deletion-policy.md`).
**Example:** `DELETE /api/columns/<id>` sets `deleted_at` on the column and on each of its cards; `GET /api/boards/<id>` no longer returns them.

## DB-04 Order siblings with a FLOAT column

**Rule:** Sortable siblings (`columns.order`, `cards.order`) use `db.Column(db.Float, nullable=False)`. Append at `max(order) + 1024`. Insert between neighbours at their midpoint. Always read with `ORDER BY order, created_at, id` so ties are deterministic. Rebalance a sibling set to multiples of 1024 when any gap falls below `1e-6`.
**Rationale:** A float lets a move write exactly one row instead of renumbering a whole column, which keeps drag-and-drop cheap and avoids write conflicts. The explicit gap and tie-break rules stop precision loss from corrupting order.
**Example:** Dropping a card between orders `1024.0` and `2048.0` stores `1536.0`. See `docs/contracts/ordering.md`.

## DB-05 Declare foreign keys with an explicit delete behaviour and an index

**Rule:** Each `db.ForeignKey` sets `ondelete` deliberately (`CASCADE` for containment, `SET NULL` for optional references, `RESTRICT` for authorship) and every foreign key used in a filter or join has `index=True`.
**Rationale:** Implicit defaults hide data-loss behaviour, and unindexed foreign keys turn board loads into sequential scans.
**Example:** `cards.column_id` is `CASCADE` and indexed; `cards.assignee_id` is `SET NULL`; `comments.user_id` is `RESTRICT`.

## DB-06 Enforce business uniqueness in the database

**Rule:** Anything that must be unique is a `UniqueConstraint` or `unique=True` column, not only a service check. Store emails lower-cased.
**Rationale:** Two concurrent requests both pass an application-level check. Only the database can reject the second one.
**Example:** `users.email` is unique, and `board_members` has `UniqueConstraint("board_id", "user_id")`.

## DB-07 Name constraints through one naming convention

**Rule:** `extensions.py` passes a `MetaData(naming_convention=...)` to `SQLAlchemy`, and named `CheckConstraint`s always get a `name=`.
**Rationale:** Without stable names, Alembic cannot drop or alter constraints reliably on PostgreSQL, and autogenerated diffs are noisy.
**Example:** The role check on `board_members` becomes `ck_board_members_role_valid`.

## DB-08 Change the schema only through reviewed migrations

**Rule:** Schema changes go through `flask db migrate`, and the generated revision is read and edited before it is committed. Never edit a revision that has been applied anywhere. Add a new one. Never call `db.create_all()` outside tests.
**Rationale:** Autogenerate misses renames and server defaults. Production must be reproducible from `flask db upgrade` alone.
**Example:** `migrations/versions/0001_initial_schema.py` is the reviewed revision that creates all eight tables; CI runs `flask db upgrade` against PostgreSQL.

## DB-09 Load nested data with explicit queries

**Rule:** Endpoints that return nested data (`GET /api/boards/<id>`) load it with a fixed number of queries using joins, `joinedload`, or one `IN` query per level. Never touch a lazy relationship inside a loop.
**Rationale:** An N+1 query pattern makes board load time grow with card count.
**Example:** The board detail loads members, columns, and cards in three queries regardless of how many cards exist; a test asserts the query count.

## DB-10 Normalize the connection URL for the driver

**Rule:** `config.py` rewrites `postgres://` and `postgresql://` to `postgresql+psycopg://`, enables `pool_pre_ping`, and leaves TLS to the URL (`?sslmode=require` on hosted databases).
**Rationale:** Hosted providers hand out driver-less URLs, and idle pooled connections are dropped by the platform.
**Example:** Helipod's `postgresql://...` value works unchanged as `DATABASE_URL`.
